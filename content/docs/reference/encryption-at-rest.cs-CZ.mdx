---
title: Šifrování uložených dat
description: Šifrování obálkou AES-256-GCM pro citlivá pole databáze.
---

Riffado šifruje uživatelská obsahová pole v databázi algoritmem AES-256-GCM,
kdy klíč je odvozen z proměnné prostředí `ENCRYPTION_KEY`, kterou již runtime
vyžaduje.

Jedná se o **šifrování obálkou s klíčem uloženým na serveru.** Nejde o zero-knowledge šifrování.

<span id="what-is-encrypted" />

## Co je šifrováno

| Sloupec | Typ | Poznámky |
|---|---|---|
| `recordings.filename` | text | Často obsahuje informace o tématu (např. AI-generované názvy) |
| `transcriptions.text` | text | Úplný přepis |
| `ai_enhancements.summary` | text | Shrnutí pomocí LLM |
| `ai_enhancements.key_points` | jsonb | Uloženo jako obálka `{ "c": "v1:..." }` |
| `ai_enhancements.action_items` | jsonb | Stejný formát obálky |
| `user_settings.summary_prompt` | jsonb | Konfigurace vlastních promptů může obsahovat uživatelský kontext |
| `user_settings.title_generation_prompt` | jsonb | Stejné |
| `recording_tasks.text`, `.assignee_hint`, `.due_phrase`, `.quote` | text | Úkol, název slyšený pro vykonavatele, termín a slova, ve kterých to bylo řečeno |
| `task_update_proposals.due_phrase`, `.quote` | text | Následný úkol slyšený na pozdější nahrávce |

Návrh úkolu, který jste odmítli, se ukládá pouze jako HMAC jeho znění
(`recording_task_rejections.fingerprint_hmac`), aby nebyl stejný úkol navržen znovu; samotné znění
úkolu se neukládá.

Předchozí šifrování (beze změny):

- `plaud_connections.bearer_token`
- `api_credentials.api_key`

Mimo rozsah této vrstvy:

- **Zvukové soubory v úložišti** (lokální FS / S3). Šifrování na úrovni objektu je
  samostatná, náročnější změna. Pro S3 doporučujeme v současnosti server-side šifrování
  na úrovni bucketu; k šifrování na úrovni jednotlivých objektů v aplikaci se lze
  případně vrátit později.
- **Vyhledávání.** Fulltextové vyhledávání v přepisech zatím není implementováno,
  takže šifrováním `text` nedochází ke zhoršení funkce. Pokud bude vyhledávání
  doplněno později, bude potřeba HMAC index ztokenizovaných dat — nikoliv tato úprava.

<span id="what-this-protects-against" />

## Proti čemu toto chrání

- Odcizené zálohy nebo snapshoty databáze
- Přístup k read-replikám bez přístupu k aplikačnímu serveru
- SQL-injection, která pouze čte, ale nespouští kód aplikace
- Operátoři s přístupem pouze k databázi (např. přes administrační konzoli)
  nemohou číst obsah, aniž by měli také klíč aplikačního serveru

<span id="what-this-does-not-protect-against" />

## Proti čemu toto nechrání

- Kompromitovaný aplikační server. Server drží klíč a dešifruje obsah v době
  požadavku, aby nad ním mohl spouštět AI. Toto je nevyhnutelné, dokud jsou
  serverová transkripce a sumarizace součástí produktu.
- Kompromitovaná `ENCRYPTION_KEY`. S klíčem nakládejte stejně jako s hlavním
  přihlašovacím údajem do databáze.
- Kompromitovaný poskytovatel AI. Otevřený text je zasílán kterémukoliv
  poskytovateli pro přepis / vylepšení, kterého si uživatel zvolí. Tato důvěrná
  hranice je na volbě uživatele a je nezávislá na této vrstvě.

Pokud potřebujete, aby se otevřený zvuk a přepisy vůbec nedostaly na infrastrukturu třetích stran,
provozujte lokálního AI poskytovatele (Ollama nebo LM Studio)
na stejném stroji jako Váš Riffado instance. Server stále drží
šifrovací klíč, ale žádný otevřený text neopouští Vaše zařízení.

<span id="key-management" />

## Správa klíčů

`ENCRYPTION_KEY` musí být 64znakový hexadecimální řetězec (32 bytů). Vygenerujte jej pomocí:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Ztráta klíče znamená, že šifrovaný obsah nebude možné obnovit. Klíč
zálohujte odděleně od databáze.

Soubory záloh vytvořené nástrojem `/api/backup` jsou **v otevřeném textu** záměrně —
jde o uživatelský export. Ukládejte je stejně pečlivě, jako byste ukládali
nešifrovanou databázi.

<span id="versioning-and-key-rotation" />

## Verze a rotace klíčů

Nový šifrovaný text zapisovaný touto vrstvou je opatřen prefixem `v1:`. Starší formáty
zůstávají čitelné:

- `v1:iv:tag:hex` — aktuální. Identifikuje klíč/verzi, která jej vytvořila.
- `iv:tag:hex` (bez prefixu) — předchozí formát používaný pro Plaud bearer
  tokeny a AI klíče. Čtecí cesta jej toleruje.
- Cokoli jiného — považováno za starý otevřený text a vrací se beze změny. Toto
  slouží jako kompatibilní okenko mezi nasazením a zpětným přepisem.

Rotace klíčů zatím není implementována. Prefix `v1:` je zde, aby bylo v budoucí
vlně rotace možné určit, které řádky je třeba přešifrovat.

<span id="backfill" />

## Zpětné šifrování

Řádky existující před nasazením zůstávají v otevřeném textu, dokud nejsou přepsány. Čtecí cesta
během tohoto období toleruje oba formáty. Pokud chcete existující řádky zašifrovat ihned:

**Docker / vlastní hosting (preferovaná cesta):** skript je součástí
image na adrese `/app/encrypt-backfill.js`.

```bash
# Report what would change (no writes)
docker compose exec app bun encrypt-backfill.js --dry-run

# Apply
docker compose exec app bun encrypt-backfill.js
```

**Ze zdrojového kódu (vývoj):**

```bash
bun scripts/encrypt-backfill.ts --dry-run
bun scripts/encrypt-backfill.ts
```

Skript je idempotentní (přeskakuje řádky již ve formátu `v1:`), pracuje po dávkách
a lze jej bezpečně přerušit a později opět spustit.
