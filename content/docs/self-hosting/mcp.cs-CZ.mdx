Samoobslužný Klepna, který se přihlašuje přes [jednotné přihlášení](./sso),
může také poskytovat koncový bod MCP (Model Context Protocol). Lidé k němu
připojí svého AI klienta a ptají se na své nahrávky; serverové služby
čtou, co Organizace ví. Klepna zde funguje jako server chráněných zdrojů:
tokeny vydává realm a oprávnění tokenu určují, do jakých oblastí
se volající dostane. V režimu `AUTHZ_MODE=idp` se čtou z položky `scope`
odděleného mezerami. Režim `AUTHZ_MODE=local` zachovává původní klientské
role Keycloaku (`resource_access[MCP_AUDIENCE].roles`).

Server je pouze pro čtení, s výjimkou jedné věci: stav a zadání úkolu.

<span id="what-it-exposes" />

## Co server poskytuje

Šest oprávnění zpřístupňuje šest oblastí. Volající vidí pouze povolené
nástroje. Volání známého nástroje bez potřebného oprávnění vrátí
403 `insufficient_scope`; neznámý název vrátí "Unknown tool".

| Oprávnění          | Nástroje                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| `knowledge:read`   | `list_types`, `list_knowledge`, `find_knowledge`, `get_entity`, `get_facts`, `list_mishearings`    |
| `transcripts:read` | `get_transcript`, `search_transcripts`                                                             |
| `summaries:read`   | `get_summary`, `search_summaries`                                                                  |
| `tasks:read`       | `list_tasks`, `search_tasks`                                                                       |
| `tasks:write`      | `update_task` (pouze stav a zadání)                                                            |
| `mail:read`        | `list_mail`, `get_mail`, `search_mail`                                                             |

`list_folders` a `list_recordings` jsou dostupné spolu s některou z
`transcripts:read`, `summaries:read` nebo `tasks:read`.

- **Almanach** (`knowledge:read`): lidé a věci, jejich typy,
  popisy, další názvy (aliasy a tak jak je rozpoznala funkce přepisu),
  fakta a špatně rozpoznaná slova (tvary zadané jako slyšené, slova
  uživatelsky opravená v přepisech – s korekcí).
- **Přepisy** (`transcripts:read`): přepis, jak jej lidé vidí v
  Klepna, aplikované potvrzené opravy, jménem označení mluvčí tam, kde
  byli potvrzeni, časované repliky.
- **Shrnutí** (`summaries:read`): text shrnutí a klíčové body.
- **Úkoly** (`tasks:read`): otevřené, dokončené a zrušené úkoly.
  Návrhy čekající na kontrolu se nikdy nevypisují.
- **Pošta** (`mail:read`, kde instance [přijímá poštu](../user-guide/mail)): e-maily
  v hromádce, jejich účastníci, text po částech (citované zprávy s
  uváděným autorem), přílohy podle názvu a velikosti a se
  `summaries:read` jejich souhrn. Každý výsledek s poštou nese
  `untrusted: true`: poštu píšou lidé zvenčí. Tajné adresy jsou skryté,
  i pro jejich vlastníka.

Oprávnění se kombinují a některá pole vyžadují dvě:

- Důkaz faktu (až tři citace s nahrávkou a pozicí)
  vyžaduje `transcripts:read` i `knowledge:read`; důkaz v e-mailu
  vyžaduje místo toho `mail:read`.
- Úkoly a fakta naučená z pošty se vypisují se samotnými `tasks:read` a
  `knowledge:read`, označené `kind: "mail"` (úkoly) nebo
  `origin: "mail"` (fakta). Jejich citace, slovní termín a e-mail (název
  a odkaz) přicházejí jen s `mail:read` a bez ní vyhledávání nikdy
  nenajde slova e-mailu.
- Akční položky shrnutí v `get_summary` a v tom, co
  `search_summaries` vyhledává, vyžadují `tasks:read`.
- Filtr `entity` u nástrojů nad nahrávkami a `search_mail` vyžaduje `knowledge:read`.
- `tasks:write` zahrnuje `tasks:read`.

Oprávnění nikdy nerozšiřuje rozsah již viděných dat: běžná pravidla aplikace Klepna
vybírají řádky (viz [Co volající vidí](#what-callers-see)).

Pole `language` nástroje `get_transcript` zůstává jazykem rozpoznaným poskytovatelem. `confirmed_language` je uživatelem potvrzený jazyk nahrávky jako kód ISO 639-1, nebo `null` při volbě Automaticky; `detected_language` opakuje původní odhad poskytovatele. Také `list_recordings` obsahuje `confirmed_language`. Tato pole nemění text přepisu.

## Zapnutí serveru

```bash
MCP_AUDIENCE=chatterbox-mcp          # client id of the resource client below
# MCP_ALLOWED_CLIENTS=claude,claude-code,acme-reports
# MCP_AUDIT_RETENTION_DAYS=90
# For Claude from the internet, see the Claude and Claude Code page:
# MCP_PUBLIC_INGRESS_HEADER=X-MCP-Ingress
# MCP_PUBLIC_CLIENTS=claude
# MCP_CONNECTOR_KEYS=claude=<openssl rand -hex 32>
# MCP_RESOURCE_AUDIENCE=false
```

- Server vyžaduje jednotné přihlášení (`OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`,
  `OIDC_CLIENT_SECRET`) a `APP_URL`. Bez nich se server nespustí a vypíše
  "MCP_AUDIENCE needs single sign-on (OIDC_ISSUER_URL, OIDC_CLIENT_ID,
  OIDC_CLIENT_SECRET)" nebo "MCP_AUDIENCE needs APP_URL".
- Tokeny musí pocházet z realmů jednotného přihlášení. Samostatné
  nastavení vydavatele není: druhý realm by mohl vydat token, jehož `sub`
  se bude shodovat se skutečným uživatelem.
- Při nezadané hodnotě `MCP_AUDIENCE` odpovídá `/api/mcp` a jeho metadata 404.
- Hostovaná Klepna jednotné přihlášení ignoruje, takže server zde zůstává vypnutý.
- `docker-compose.yml` předává všechny tyto proměnné dál.
- Při prázdném `MCP_ALLOWED_CLIENTS` server při startu zapíše do logu
  varování: volat smí kterýkoliv klient realmu, jehož token nese potřebná oprávnění.

Klepna načítá `issuer` realmu a podpisové klíče z
`<OIDC_ISSUER_URL>/.well-known/openid-configuration`. Hodnota `iss`
tokenu musí být přesně stejně jako `issuer`. Když je `OIDC_ISSUER_URL`
interní adresa (například služba v compose), opravte veřejný název hostitele v Keycloaku (`KC_HOSTNAME`), ať realm uvádí
stejného vydavatele pro Klepna i klienty, kteří získávají tokeny.

## Nastavení Keycloak

Ruční mapování rolí níže popisuje **`AUTHZ_MODE=local`**.
Pro **`AUTHZ_MODE=idp`** nastavte [role poskytovatele](./sso#authorization-from-the-identity-provider)
a následující MCP konfiguraci. Statický lokální realm slouží jako funkční příklad:

- Osoba potřebuje `use`, nikoli MCP role chráněných zdrojů. Každý dotaz omezuje sdílení dat.
- Pro každé výše uvedené oprávnění vytvořte rozsah oprávnění klienta OIDC se zapnutým
  **Include in token scope**. Klientům připojte jen povolená oprávnění.
  Výchozí rozsahy oprávnění se udělují i při požadavku pouze na `openid`; volitelné rozsahy oprávnění
  musí klient výslovně požadovat. Vynechání výchozího rozsahu oprávnění jej z tokenu neodebere.
- Každému MCP klientovi přidejte mapování příjemce pro ID klienta chráněných zdrojů
  (`MCP_AUDIENCE`), nezávisle na rolích. Pro `MCP_RESOURCE_AUDIENCE=true`
  zahrňte také `<APP_URL>/api/mcp` jako vlastního příjemce.
- Vypněte Full Scope Allowed a z mapování rozsahů oprávnění MCP klientů vynechte webové
  a administrátorské role. Servisní klienti v tomto režimu MCP role nepotřebují.
- Servisní klienti používají jen přihlašovací údaje klienta, níže popsané označení služby
  a záznamy v `MCP_SERVICE_CLIENTS` i `MCP_ALLOWED_CLIENTS`.
- Osobní a organizační konektor mohou mít odlišná ID a tajné klíče, například
  `claude` a `claude-enterprise`. Oba jednají za přihlášeného člověka a nepatří
  do `MCP_SERVICE_CLIENTS`.

Při přechodu z MCP rolí na IdP režim nastavte rozsahy oprávnění a získejte nové
tokeny. Tokeny s pouhými rolemi v IdP režimu MCP oprávnění neudělují.
Lokální režim zachovává ruční postup s rolemi níže.

<details>
<summary>Krok 1: klient chráněných zdrojů</summary>

1. **Clients → Create client**, typ **OpenID Connect**, ID klienta
   `chatterbox-mcp` (hodnota `MCP_AUDIENCE`).
2. **Client authentication:** vypnuto. Vypněte veškeré autentizační toky:
   do tohoto klienta se nikdo nepřihlašuje; nese pouze role.
3. **Roles → Create role**, šestkrát: `knowledge:read`,
   `transcripts:read`, `summaries:read`, `tasks:read`, `tasks:write`,
   `mail:read`.
4. Přiřaďte role uživatelům či skupinám, kteří mohou danou oblast využívat
   (**Role mapping → Assign role → Filter by clients**).

Není třeba žádné mapování příjemce. Výchozí rozsah oprávnění klienta `roles` v realmu
nese mapování pro určení příjemce (audience-resolve), které přidává `chatterbox-mcp` do `aud`
vždy, když některá jeho role je obsažena v tokenu, a ukládá role pod
`resource_access.chatterbox-mcp.roles`, odkud je čte Klepna. Klepna ověřuje, že v
`aud` je `MCP_AUDIENCE`.

</details>

<details>
<summary>Krok 2: klienti pro uživatele (AI klienti)</summary>

Jeden klient na aplikaci, aby bylo možné přístupy omezit a rozlišit v
přístupovém logu.

1. **Create client**, typ **OpenID Connect**. **Client authentication:**
   vypnuto (veřejný klient). **Authentication flow:** pouze Standard flow.
2. **Valid redirect URIs:** adresy, které dokumentuje aplikace.
3. **Advanced → Proof Key for Code Exchange Code Challenge Method:**
   `S256`.
4. **Client scopes → `<client>-dedicated` → Scope:** vypněte **Full scope
   allowed**, poté **Assign role** a vyberte role `chatterbox-mcp`,
   které aplikace smí mít.

Token pak obsahuje role, které má uživatel **a zároveň** které povoluje účel klienta.
Například poznámková aplikace, která má vyhledávat pouze v
shrnutích, dostane pouze `summaries:read`, i když uživatel vlastní všech šest rolí.

</details>

<details>
<summary>Krok 3: servisní účty (serverové služby)</summary>

1. **Create client**, typ **OpenID Connect**. **Client authentication:**
   zapnuto. **Authentication flow:** pouze Service accounts roles.
2. **Service accounts roles → Assign role:** role `chatterbox-mcp`, které serverová služba
   potřebuje.
3. Doporučeno: **Credentials → Client Authenticator:** Signed JWT
   (`private_key_jwt`) místo sdíleného tajemství a
   **Advanced → Access Token Lifespan** na 5 až 15 minut.

Uveďte klienta v `MCP_SERVICE_CLIENTS` (a `MCP_ALLOWED_CLIENTS`) a
přidejte mu mapování **hardcoded claim**: položku `chatterbox_subject_kind`,
hodnota `service`, pouze do přístupového tokenu. Za službu se považuje jen takový token; samotná položka `client_id`
z Keycloaku jím po nastavení `MCP_SERVICE_CLIENTS` už token neudělá.
Servisní účet jedná v datovém kontextu Organizace, takže je potřeba mít
povolenou [Organizaci](./organization) (`SELF_HOST_MODE=shared` a
`ORG_ACCOUNT_EMAIL`). Jinak jsou volání odmítnuta.

</details>

<details>
<summary>Krok 4: výměna tokenu</summary>

Serverová služba, která už drží token uživatele, jej může vyměnit za token pro
Klepna pomocí **standard token exchange** v Keycloaku (V2,
Keycloak 26.2 a vyšší): zapněte **Standard token exchange** u klienta
serverové služby a požadujte `audience=chatterbox-mcp`. Token uživatele
musí být vydán pro tuto serverovou službu (klient v `aud`). Výsledkem je
stále uživatel, s rolemi, které nový token nese.

Při výměně nevydávejte obnovovací tokeny (klient **Advanced → Allow refresh
token in Standard Token Exchange:** No), takže přístup serverové služby končí s
tokenem, který dostane. Ověřte si nastavení pro svou verzi Keycloak.

**Legacy token exchange (V1) s impersonací není podporováno** a musí
zůstat vypnuto. Klient oprávněný k impersonaci může totiž vytvořit
token pro libovolného uživatele (`requested_subject`) bez jeho tokenu, přihlášení,
MFA nebo souhlasu. Klepna určuje volajícího podle `sub`, a takový
token by četl soukromé nahrávky a znalosti uživatele, změny úkolů by
byly zaznamenány jako jeho. Token nelze odlišit od skutečného
přihlášení; odlišit ho lze pouze podle `azp` (klient) v
přístupovém logu.

- Nechte vypnutou experimentální funkci `token-exchange` (výchozí od
  Keycloak 26.2); žádnému klientovi nepřidělujte oprávnění *impersonate*.
- Omezte roli správce `impersonation`. Správci realmů se mohou vždy
  přihlásit jako jakýkoliv uživatel; Klepna je považuje za plně důvěryhodné.
- Nastavte `MCP_ALLOWED_CLIENTS` na klienty, které jste nakonfigurovali, jako
  druhou obrannou linii proti špatně nastavenému realmu.

</details>

## Připojení klientů

| Co                         | Kde                                                         |
| -------------------------- | ----------------------------------------------------------- |
| Koncový bod MCP               | `<APP_URL>/api/mcp`                                      |
| Metadata o chráněném zdroji | `<APP_URL>/.well-known/oauth-protected-resource/api/mcp` |

Koncový bod používá bezstavové Streamable HTTP: pouze `POST`,
odpovědi v JSON, žádné relace ani události odesílané serverem, jedna JSON-RPC
zpráva na jeden požadavek. Dávka (pole JSON) je odmítnuta s 400 a
JSON-RPC chybou `-32600`, MCP 2025-06-18 zrušilo dávkové zpracování. Dotaz bez
použitelného tokenu dostává 401
s `WWW-Authenticate: Bearer resource_metadata="…", scope="openid"`
(a s `error="invalid_token"`, pokud byl token poslán). Hlavička odkazuje na
metadata, kde je realm jako autorizační server a `openid` jako rozsah oprávnění,
o který má klient žádat. Bez uvedeného rozsahu oprávnění by klient žádal o všechny
rozsahy oprávnění, které realm nabízí, a Keycloak by přihlášení odmítl s
`invalid_scope`. Tato metadata jsou také dostupná na `<APP_URL>/.well-known/oauth-protected-resource`.

Pravý token realmu, který nebyl vydán pro tento server (například
token přihlašovacího webového klienta), odpoví 403, ne 401: 401
by klienta poslala znovu přihlašovat, pro stejný token.

Každé klientské aplikaci zadejte ID klienta, které jste pro ni
vytvořili v kroku 2. Dynamická registrace klientů není k tomu potřeba.
Otevřené anonymní registrace povolujte pouze pokud klient opravdu
nemůže použít předregistrované id, a pak jen se zásadou **Trusted Hosts**
omezující, kdo může registraci provést. `MCP_ALLOWED_CLIENTS` obsahuje pevné
ID klientů, čímž současně nepustí dynamicky registrované klienty.

Servisní účet ručně:

```bash
TOKEN=$(curl -s https://sso.example.com/realms/acme/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=acme-reports -d client_secret=... \
  | jq -r .access_token)

curl -s https://chatterbox.example.com/api/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## Claude a Claude Code

Claude (claude.ai, Claude Desktop, mobilní aplikace a Cowork) a Claude
Code se připojují přes přihlášení realmu. Claude na server přistupuje z
cloudu Anthropicu, takže potřebuje úzký veřejný vstup a důvěrného
klienta v Keycloaku. Stránka [Claude a Claude Code](./claude) vás
provede klienty v Keycloaku, nastavením aplikace Klepna, reverzní proxy,
konektorem i kontrolami.

## Co volající vidí

| Token                                                   | Volající                                                 |
| ------------------------------------------------------- | -------------------------------------------------------- |
| `sub` uživatele, který se přihlásil do Klepna přes SSO | Tento uživatel. Almanach: jeho a Organizace. Nahrávky: jeho a ty sdílené Organizací, jak je vidí v seznamu nahrávek. |
| Chybí takový `sub`, klient je v `MCP_SERVICE_CLIENTS` a token nese označení služby | Servisní účet jednající v datovém kontextu Organizace. Almanach: pouze Organizace. Nahrávky: pouze sdílené Organizací. Bez `MCP_SERVICE_CLIENTS` v režimu `local` jakýkoli token s `client_id` (zastaralé). |
| Cokoli jiného                                           | Odmítnuto s 403 "Sign in to Klepna once first".       |

Účty nejsou nikdy vytvořeny z tokenu: člověk se musí nejdřív alespoň
jednou přihlásit do aplikace Klepna, než jeho AI klient může server volat.
Token bez kteréhokoliv ze šesti oprávnění dostane 403 "This token carries no
Klepna MCP permission". Pozastavený účet, klient mimo `MCP_ALLOWED_CLIENTS`,
servisní účet bez zapnuté Organizace, klient, kterého veřejný vstup
neobsluhuje, a klient bez svého klíče konektoru dostanou 403
"Forbidden". Důvod uvádí log aplikace (viz
[Když se Claude nepřipojí](./claude#when-claude-cannot-connect)).

**Úkoly** kopírují logiku stránky Úkoly:

- Uživatel vidí úkoly u svých nahrávek a e-mailů a u sdílených
  Organizací ty, které jsou mu přiřazeny. Servisní účet vidí úkoly
  všech sdílených nahrávek a e-mailů.
- S `tasks:write` může `update_task` nastavit úkol jako hotový, znovu otevřený nebo
  zrušený, či změnit jeho zadání. Dokončení a znovuotevření úkolu vyžaduje `can_close`
  (majitel nahrávky, přiřazený uživatel u sdílené nahrávky nebo Organizace).
  Zrušení, znovuotevření zrušeného úkolu a přeřazení vyžadují `can_edit`
  (majitel privátní nahrávky, u sdílené pouze Organizace, tedy servisní účet).
  U sdílené nahrávky lze úkol přiřadit pouze lidem z Organizace.
- Každý úkol obsahuje `version`; `update_task` jej vyžaduje a úkol změněný
  mezitím odpoví svým aktuálním stavem místo úpravy.
- Návrhy úkolů nelze upravovat: kontrola zůstává v aplikaci. Text úkolu,
  termín splnění i nové úkoly je možné zadávat pouze v aplikaci.
- Změna je zaznamenána na uživatele či na účet Organizace (u servisních
  účtů); přístupový log uvádí klienta.

**Názvy fungují všude, kde id.** `entity`, `person`, `assignee` a
`recording` přijímají id nebo text. Lidé a věci se hledají podle jména,
aliasu, slyšeného tvaru nebo tvarů slov; nahrávky podle názvu, z
nejnovějších 500, které volající vidí. Jasná shoda se použije a vrátí se
jako `resolved`; nejasná odpoví až pěti kandidáty. Bez
`knowledge:read` se rozpoznávají pouze lidé, které už volající zná
(potvrzení mluvčí nahrávek, přiřazení úkolů), nikoli věci.

**Vyhledávání má limity.** Názvy, přepisy, shrnutí, úkoly a pošta jsou při
uložení šifrovány (šifrování uložených dat), takže vyhledávání dešifruje za
chodu vždy od nejnovějšího, s limitem:

| Vyhledávání                        | Čte maximálně  | Vrací maximálně                  |
| ---------------------------------- | -------------- | ------------------------------- |
| `list_recordings` s `title`      | 500 nahrávek    | 50                               |
| `search_transcripts`                | 200 nahrávek    | 50 nahrávek, 3 úryvky na každou  |
| `search_summaries`                  | 500 shrnutí      | 50 nahrávek, 3 úryvky na každou  |
| `search_mail`                       | 500 e-mailů    | 50 e-mailů, 3 úryvky na každý |
| `search_tasks`                      | 2000 úkolů      | 50                               |

Každé také končí nejpozději za 10 sekund. Odpověď uvádí `scanned`,
`complete` a `continue_before`; pošlete zpět `continue_before` jako `before`
(respektive jako `cursor` pro `list_recordings`), pokud chcete hledat hlouběji.
Hledání ignoruje diakritiku a velikost, rozpoznává tvary slov v jazyce
nahrávky. Výpisy mají stránkování po 50 položkách přes `next_cursor`
(u `list_mishearings` 200); `get_transcript` stránkuje podle ~40 000 znaků,
případnou delší repliku rozsekne do částí se zachováním mluvčího a času.

Popisy nástrojů říkají modelu v klientovi, že vrácený text je to, co lidé
skutečně řekli, tedy data, nikoliv instrukce.

<span id="with-authorization-from-the-identity-provider" />

## S oprávněním od poskytovatele identity

S [`AUTHZ_MODE=idp`](./sso#authorization-from-the-identity-provider):

- Token osoby funguje jen tak dlouho, dokud osoba má `use`: při každém
  volání se znovu kontroluje proti jejímu ověřenému přístupu (403 "Your
  access to Klepna has been withdrawn"; 503, dokud ho nelze ověřit).
- Službou je pouze token klienta uvedeného v `MCP_SERVICE_CLIENTS`, který
  realm označí jako službu (`chatterbox_subject_kind: service`, nastavuje
  mapování **hardcoded claim** u klientů určených jen pro služby). Token nesoucí pouze
  `client_id` patří osobě a je odmítnut, pokud se tato osoba nepřihlásila.
  Služba nikdy nespravuje přístup a nikdy není kurátorem Organizace.
- Tokeny přihlašovacího klienta (`OIDC_CLIENT_ID`) nikdy nejsou MCP
  přihlašovacími údaji. Administrátorské role ponechte mimo rozsah oprávnění
  všech MCP klientů.

V obou režimech:

- Přístupové tokeny musí uvádět `typ: Bearer` (přístupové tokeny Keycloaku to
  dělají); ID token, obnovovací token nebo token bez typu je odmítnut (401).
- `tasks:write` s sebou přináší `tasks:read`.
- Volání nástroje, který oprávnění tokenu nepokrývají, odpoví 403 s
  `WWW-Authenticate: Bearer error="insufficient_scope", scope="<permissions>"`.
  Metadata zdroje uvádějí `openid` a šest oprávnění v
  `scopes_supported`; vytvořte rozsah oprávnění klienta s názvem každého
  oprávnění, takže klient, který o ně požádá, dostane ta, která mít smí,
  a zbytek realm odmítne (`invalid_scope`).

<span id="limits-and-audit" />

## Limity a audit

| Limit                                | Hodnota                                 |
| ------------------------------------- | --------------------------------------- |
| Požadavky na volajícího (subjekt a klient), včetně odmítnutých | 60 za minutu  |
| Hledání na volajícího                | 10 za minutu                            |
| Velikost těla žádosti                | 256 KB (nad tím 413)                    |

Hledání jsou nástroje `search_*`, `list_recordings` s `title`,
`list_mishearings` (čte knihovny oprav) a všechny
`recording` zadané jako název místo id. Po překročení limitu odpověď
bude 429 s `Retry-After`; hledání nad svůj limit odpoví "Příliš mnoho hledání;
zkuste za minutu znovu". Limit na IP klienta není: všichni uživatelé
Claude přicházejí z několika stejných adres Anthropicu. Objem omezte na
reverzní proxy. Sloupec `ip` v přístupovém logu vyžaduje
`RATE_LIMIT_TRUST_PROXY_HEADERS=true` za proxy, která přeposílací
hlavičky přepisuje (viz [Proměnné prostředí](./environment-variables)).
Pokud není dostupný dokument metadat realmu nebo podpisové klíče,
koncový bod odpovídá 503 místo 401, takže klient nezahodí dobrý token.

Každý volání nástroje a každý validní token bez přiřazeného volajícího
zapisuje jeden řádek do tabulky `mcp_access_log`:

| Sloupec        | Obsah                                                           |
| -------------- | --------------------------------------------------------------- |
| `at`          | Kdy                                                          |
| `caller_kind` | `user` nebo `service`; prázdné, pokud token neměl volajícího     |
| `user_id`     | Uživatel v aplikaci Klepna (prázdné, pokud je účet smazán)               |
| `subject`     | `sub` tokenu                                                |
| `client_id`   | `azp` tokenu, jinak `client_id`                                |
| `tool`        | Nástroj, který byl volán                                      |
| `outcome`     | `ok`, `denied`, `conflict`, `not_found`, `invalid` nebo `error` |
| `target_ids`  | ID nahrávek, úkolů nebo záznamů přečtených či změněných (max. 200)  |
| `ip`          | IP klienta, pokud známá                                      |

Argumenty a obsah se neukládají. Řádky starší než
`MCP_AUDIT_RETENTION_DAYS` (výchozí 90) jsou mazány hodinovým
údržbovým úkolem, i po vypnutí serveru. Obrazovka pro log zatím není;
tabulku je nutné dotazovat přímo.

`MCP_ALLOWED_CLIENTS` (čárkou oddělená ID klientů) odmítá tokeny, jejichž
`azp` není v seznamu, jak pro uživatele tak pro servisní účty.
Pokud není nastaveno, může volat libovolný klient realmu, jehož token
projde kontrolou příjemce a oprávnění.

Tokeny se kontrolují na přesného vydavatele, `aud` obsahující
`MCP_AUDIENCE` (nebo URL koncového bodu MCP při
`MCP_RESOURCE_AUDIENCE=true`), expiraci (toleruje se 30 sekund rozdílu v čase),
`RS256`, `PS256` nebo `ES256` podpis a profil přístupového tokenu poskytovatele.
Adaptér Keycloaku vyžaduje `typ: Bearer`, i v lokálním režimu.
Klepna je nikdy neposílá dál.

## Vyzkoušení lokálně

Realm Keycloaku pro testování celého systému ze stránky [Jednotné přihlášení](./sso#trying-it-locally)
obsahuje klienty MCP: `riffado-mcp`, `riffado-mcp-tester`,
`riffado-mcp-bot`, `claude` a `claude-code`. Volitelný test
`src/tests/mcp/keycloak.integration.test.ts` se přes ně přihlašuje stejně
jako Claude (jeho hlavička popisuje spuštění), s
`docker-compose.e2e.sso-resource-indicators.yml` i bez něj.
