title: AI providers
description: Configure OpenAI-compatible transcription and summarization providers.
---

Chatterbox uses the OpenAI SDK with a configurable `baseURL`. Any provider
that exposes an OpenAI-compatible API works: OpenAI itself, Groq,
OpenRouter, Together, Azure OpenAI, LM Studio, Ollama, and anything else
that speaks the same wire format.

Three transcription backends are wired in natively because their APIs
are not OpenAI-compatible: Google Gemini, ElevenLabs Scribe and
Speechmatics.

You can configure multiple providers. Processing profiles choose the
provider and model for each step; a manual transcription uses the account
default, while a manual summary can run with any available profile.

## Adding a provider

**Settings → AI providers → Add provider** opens a dialog with a preset
list. Each preset pre-fills `baseURL`, default model, and a hint about
which API surface the transcription worker should use:

- **Whisper-style** (`/v1/audio/transcriptions`, multipart upload) — the
  classic OpenAI Whisper surface. Used by OpenAI, Groq Whisper, Together
  Whisper, LM Studio, Ollama.
- **Chat-style** (`/v1/chat/completions` with an `input_audio` content
  part) — for providers that expose audio-input LLMs instead of a
  dedicated transcription endpoint. Used by OpenRouter routing
  Gemini / GPT-audio / Voxtral.
- **Gemini-style** (`generateContent` with inline audio data) — the
  Google Gemini native API. Used by the Google Gemini preset.
- **Scribe-style** (`/v1/speech-to-text`, multipart upload authenticated
  with `xi-api-key`) — the ElevenLabs native API. Used by the ElevenLabs
  preset.
- **Speechmatics-style** (`POST /v2/jobs`, then poll, then download) —
  the Speechmatics Batch job API. Used by the Speechmatics preset.

Pick a preset, paste your API key, choose a default model, save. Repeat
for additional providers.

## Preset reference

| Preset      | Base URL                                     | Notes                                                            |
| ----------- | -------------------------------------------- | ---------------------------------------------------------------- |
| OpenAI      | *(blank, defaults to api.openai.com)*        | Production quality; `whisper-1`, `gpt-4o-transcribe`             |
| Groq        | `https://api.groq.com/openai/v1`             | Free Whisper API, very fast                                      |
| OpenRouter  | `https://openrouter.ai/api/v1`               | Chat-style transcription; many summarization models in one key   |
| Together AI | `https://api.together.xyz/v1`                | Cost-effective, broad model selection                            |
| Google Gemini | *(blank, native Google API)*                | Gemini-style transcription; transcription only                   |
| ElevenLabs  | *(blank, defaults to api.elevenlabs.io)*     | Scribe-style transcription, optional speaker labels; transcription only |
| Speechmatics | *(blank, auto-routing asr.api.speechmatics.com)* | Batch job transcription, optional speaker labels; transcription only |
| Azure       | `https://<resource>.openai.azure.com/...`    | Enterprise compliance, deployment-scoped URLs                    |
| LM Studio   | `http://localhost:1234/v1`                   | Local, 100% offline                                              |
| Ollama      | `http://localhost:11434/v1`                  | Local, easy model management                                     |
| Custom      | *(freeform)*                                 | Anything else OpenAI-compatible                                  |

LM Studio and Ollama presets default to `http://localhost`. From inside
a Docker container, `localhost` is the container itself, not the host
machine — use `http://host.docker.internal:<port>` on Mac/Windows, or
the Docker bridge IP on Linux, to reach an AI server running on the
host. If you run Ollama in the same Docker network as Chatterbox, use the
service hostname (`http://ollama:11434/v1`).

## Choosing models

The preset list ships with a curated set of known transcription model
ids per provider. When the API exposes structured capability metadata
(today only OpenRouter), the Add/Edit dialog can fetch the live list of
audio-capable models for you. For everyone else, the curated list drives
the dropdown and a **Custom…** option lets you type an id by hand for
new releases that ship before our next version bump.

Summarization is more forgiving — any chat model that follows the
OpenAI `chat/completions` shape works. Pick something fast and cheap
(e.g. `gpt-4o-mini`, `llama-3.1-70b-versatile`) unless you have a
specific reason to use a larger model.

### ElevenLabs Scribe

The preset offers `scribe_v2` (the default), `scribe_v2_medical`, and
the legacy `scribe_v1`. Diarization is a request flag rather than a
separate model, so the dropdown exposes it as **scribe_v2 (speaker
labels)**, stored as `scribe_v2+diarize`. With it selected, transcripts
come back as `speaker_0: …` lines, the same shape Chatterbox stores for
OpenAI's diarizing model, and the workstation renders them as a dialog
instead of a block of prose. See [How transcripts and summaries are
displayed](#how-transcripts-and-summaries-are-displayed).

Leave **Base URL** blank to use `api.elevenlabs.io`. To keep audio in a
specific region, set a residency host instead, for example
`https://api.eu.residency.elevenlabs.io`. The trailing `/v1` is
optional.

Audio is uploaded exactly as stored. The mono Opus re-encode that keeps
oversized recordings under OpenAI's 25 MiB request limit is skipped for
Scribe, which accepts multi-gigabyte uploads, so long meetings reach the
model at full quality.

Scribe v2 and v2 Medical are told which names to expect: up to 500
people and things from the [Almanac](./almanac), sent as keyterms. See
[Names from the Almanac](./almanac#names-from-the-almanac). ElevenLabs
charges keyterms as an add-on to the hourly price.

ElevenLabs is transcription only. It has no `chat/completions` endpoint,
so keep a separate provider as your summarization default.

### Speechmatics

The preset offers `enhanced` (the default, highest accuracy), `standard`
(faster and cheaper), and `melia-1`, the multilingual model that detects
and switches between languages on its own. As with Scribe, diarization is
a request setting rather than a separate model, so each one has a
**(speaker labels)** variant in the dropdown, stored as `enhanced+diarize`
and friends. With one of those selected, transcripts come back as
`speaker_1: …` lines and the workstation renders them as a dialog — see
[How transcripts and summaries are displayed](#how-transcripts-and-summaries-are-displayed).
Speechmatics' own `S1` labels are rewritten to `speaker_1` on the way in so
they read the same as every other provider's; a name that came from speaker
identification is kept as-is.

The same names from the Almanac go to Speechmatics as its custom
dictionary, each with the forms it was misheard as before.

Your **Default transcription language** is passed through as the language
code. If you haven't set one, Chatterbox asks for `auto` and lets
Speechmatics identify the language. `melia-1` is the exception: it only
accepts `multi`, so the language setting is ignored when you pick it.

Leave **Base URL** blank to use `asr.api.speechmatics.com`, which routes to
the nearest region. To pin data to one region, set the regional host
instead — `https://eu2.asr.api.speechmatics.com`,
`https://us1.asr.api.speechmatics.com`, `https://au1.asr.api.speechmatics.com`
and so on. The trailing `/v2` is optional.

Batch is an asynchronous API: Chatterbox uploads the audio as a job, polls it
every 3 seconds, downloads the transcript when the job reports `done`, and
then deletes the job so the audio and transcript don't sit on
Speechmatics' servers waiting for their retention window to expire. The
whole wait is bounded by `WHISPER_REQUEST_TIMEOUT_MS` (60 minutes by
default) — raise it if you transcribe recordings long enough to need more.

Audio is uploaded exactly as stored; the mono Opus re-encode that keeps
oversized recordings under OpenAI's 25 MiB request limit is skipped here,
as it is for Scribe.

Speechmatics is transcription only — it has no `chat/completions`
endpoint, so keep a separate provider as your summarization default.

## What gets sent to the provider

Plaintext audio (for transcription) and plaintext transcript text
(for summarization). ElevenLabs Scribe v2 and Speechmatics also get up to
500 names from your Almanac with the audio (see
[Names from the Almanac](./almanac#names-from-the-almanac)).

A summary request also carries what its task step needs: the item's effective
time (to turn "by Friday" into a date), accepted task mentions on that item,
and possible earlier tasks from the same folder scope. This lets the model
suggest a match, completion, changed deadline, drop, or reassignment. Only
tasks visible in that processing scope are sent. They go to the provider
selected by the profile used for the summary.

The trust boundary is the provider you picked.
Chatterbox's at-rest encryption protects the database, not the network
hop to your AI provider — see
[Encryption at rest](../reference/encryption-at-rest) for the explicit
list of what that layer does and does not cover.

If you need to minimise that trust boundary, run a local provider (LM
Studio or Ollama) on the same machine as a self-host instance. Both
transcription and summarization stay on your hardware.

## Choosing a provider for a run

Open **Settings → Profiles** to choose a provider and model for each step in
a processing profile. Folder defaults decide which profile a new item uses.
For a manual summary, choose any available profile beside **Summarize**. To
retry a transcription with a different provider, change the account default
or the item's profile first, then run **Transcribe** or **Re-transcribe**.

## How transcripts and summaries are displayed

**Summaries are Markdown.** The model is asked for a JSON object, and the
`summary` value inside it is written in Markdown and rendered as such:
headings, bullet and numbered lists, bold, links and tables all come
through. The instruction to format this way is appended to every prompt,
including a custom one you wrote yourself, so your own prompts do not
need to mention it.

The JSON envelope is still a bare object with no code fences around it.
If a model ignores that and answers with prose instead, the reply is
shown as-is rather than discarded, and because it is rendered as Markdown
it usually still reads correctly.

Raw HTML in a summary is dropped, not rendered.

**Diarized transcripts are shown as a dialog.** When a transcript came
from a path that labels speakers, the workstation renders one block per
turn with the speaker's name above it, colour-coded, with consecutive
turns from the same speaker grouped together. That applies to
`gpt-4o-transcribe-diarize`, `scribe_v2+diarize`, the Speechmatics
`+diarize` models, and transcripts imported from Plaud.

Every other transcript is rendered exactly as before, as plain text.
That is deliberate rather than a limitation: Gemini and the chat-style
providers are explicitly asked not to emit speaker labels, so a line in
one of those transcripts that happens to read `Note: send the deck` is
never mistaken for a speaker called "Note". A diarized transcript that
comes back without any labels — which happens when a model finds only one
voice — also falls back to plain text rather than showing a dialog with a
single anonymous participant.

Speaker names are shown close to what the provider stored: `speaker_0`
is displayed as `Speaker 0`, but it is not renumbered or renamed.
Summaries quote these labels back verbatim, so a summary that mentions
`speaker_0` still points at something you can find in the transcript.

## Automatic summaries in a profile

Open **Settings → Profiles**, edit a profile, and turn on **Run automatically**
for its summary step. A filed item reaches that step after transcription and
any Learn hold. The profile supplies the summary instructions, output language
and format, provider, task detection, and multi-pass settings.

This path is opt-in and costs at least one AI provider call per item. A
multi-pass summary costs more. Manual transcription does not bypass the
profile sequence: the later automatic steps continue according to the item's
assigned profile.

Automatic summaries require an enhancement provider selected by the profile.
The included managed transcription provider is transcription-only, so a hosted
account using only that provider needs another provider for summary steps.

### Cost guardrails

An automatic summary normally makes one LLM call. With chat models at
`$0.15-$5 / 1M input tokens` and typical 1-2k token transcripts, a
single summary is fractions of a cent, but a large import or a premium
model can add up. Two safeguards:

- **Per-user hourly cap.** Auto-summary requests are throttled by
  `AUTO_SUMMARY_RATE_LIMIT_PER_HOUR` (default `60`). When the bucket
  is exhausted, pipeline work waits behind the capped backlog. The transcript
  stays saved, and a cap deferral does not emit `summary.failed`. Manual
  summaries are not throttled by this cap.
- **Choose the model in the profile.** Each summary step names its provider
  and model explicitly. Chatterbox does not silently substitute a different
  chat model.

### Stale summaries on re-transcribe

When a recording is **re-transcribed**, its old summary and later workflow
results become **Outdated**. The pipeline rebuilds the automatic steps enabled
by the assigned profile. A manual-only result stays visible as outdated until
you run it again.

### Failure semantics

Failure is isolated: if the summary call fails, the transcript stays saved,
`transcription.completed` still fires, and `summary.failed` reports the actual
summary error. The manual **Summarize** action still works. A rate-cap deferral
is not a failure and does not emit `summary.failed`.
