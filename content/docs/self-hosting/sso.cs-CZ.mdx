Chatterbox ve vlastním hostingu může předat přihlašování poskytovateli identity OpenID Connect. Jakmile je nastaveno, je **jedinou** možností přihlášení:

- na přihlašovací stránce se zobrazuje pouze jedno tlačítko **Přihlásit se pomocí &lt;provider&gt;**;
- přihlašování e-mailem a heslem, registrace a obnova hesla jsou na serveru vypnuty, nejen skryty;
- každý, koho poskytovatel propustí, získá při prvním přihlášení účet Chatterbox. Kdo může Chatterbox používat, je rozhodnuto u poskytovatele (například přiřazením uživatelů nebo skupin ke klientovi).

S `DISABLE_REGISTRATION=true` zůstává instance uzavřená: přihlásit se mohou pouze lidé, kteří už mají účet Chatterbox, a jejich účet je propojen při prvním přihlášení přes SSO, jak je popsáno níže. Všichni ostatní uvidí hlášení, že instance nepřijímá nové účty. Pokud chcete pustit nového kolegu, proměnnou vypněte, restartujte, nechte ho jednou přihlásit a poté opět zapněte.

Hostovaný Chatterbox tyto proměnné ignoruje.

## Nastavení poskytovatele

Vytvořte důvěrného klienta OpenID Connect (authorization code flow) s těmito parametry:

- **Přesměrovací URI:** `<APP_URL>/api/auth/oauth2/callback/oidc`
- **Scope:** `openid`, `profile`, `email`
- **PKCE:** `S256` (Chatterbox vždy posílá code challenge)

Chatterbox potřebuje položky `sub`, `email`, `name` a `email_verified`.

<details>
<summary>Keycloak</summary>

1. Ve svém realm **Clients → Create client**, zvolte **OpenID Connect**,
   client id `chatterbox`.
2. **Client authentication:** zapnuto. **Authentication flow:** pouze Standard flow.
3. **Valid redirect URIs:** `<APP_URL>/api/auth/oauth2/callback/oidc`.
4. **Advanced → Proof Key for Code Exchange Code Challenge Method:** `S256`.
5. Zkopírujte tajný klíč v **Credentials**.

Issuer je `https://<keycloak-host>/realms/<realm>`.

</details>

<details>
<summary>Microsoft Entra ID</summary>

Zaregistrujte aplikaci s **Web** přesměrovacím URI výše a vytvořte klientský tajný klíč. Issuer je `https://login.microsoftonline.com/<tenant-id>/v2.0`. Entra neposílá `email_verified`; viz [Stávající účty](#existing-accounts).

</details>

Nastavte tedy:

```bash
OIDC_ISSUER_URL=https://sso.example.com/realms/acme
OIDC_CLIENT_ID=chatterbox
OIDC_CLIENT_SECRET=...
OIDC_PROVIDER_NAME="Acme SSO"     # the button label; defaults to "SSO"
# OIDC_SCOPES="openid profile email"
# OIDC_SESSION_MAX_AGE=86400       # seconds, see Sessions below
```

Chatterbox načítá endpoints poskytovatele z `<OIDC_ISSUER_URL>/.well-known/openid-configuration`. Issuer musí být `https`: Chatterbox věří ID tokenu, který získá přímo od endpoints poskytovatele, proto tento kanál musí být přes TLS. Prostý `http` je akceptován pouze pro interní hosty (`localhost`, privátní IP adresy, jednoznačné názvy jako služba compose `keycloak` a názvy `.local` / `.internal`).

Všechny tři údaje – issuer, client id a secret – musí být nastaveny; částečná konfigurace zastaví server s chybou.

## Stávající účty

Když je pro instanci zapnuto jednotné přihlášení, která již má účty, první SSO přihlášení osoby se spáruje s jejich existujícím účtem (včetně nahrávek, nastavení a všeho), **pokud se e-mail shoduje a poskytovatel jej označí jako ověřený** (`email_verified: true`).

Pokud poskytovatel adresu neověřil, Chatterbox odmítne propojit s existujícím účtem a přihlašovací stránka ukáže důvod. Ověřte e-mail u poskytovatele (v Keycloak: přepínač **Email verified** uživatele) a přihlašte se znovu. Neověřený e-mail, který zatím nikdo nepoužívá, prostě vytvoří nový účet.

Od této chvíle je účet vázán na uživatelské id poskytovatele (`sub`): jméno i e-mail odpovídají údajům u poskytovatele při každém přihlášení. E-mail, který už používá jiný účet Chatterbox, nebude převzat; uživatel si ponechá svůj stávající.

Účet je navíc vázán na issuer, který za něj ručil, bez ohledu na `AUTHZ_MODE`. Přesměrování Chatterbox na jiný realm účty nepřevezme: jejich přihlášení je odmítnuto s hlášením „belongs to a different identity provider“. Issuer se odvíjí od adresy poskytovatele, takže přesun téhož realmu na nový hostname, z `http` na `https` nebo pod nový název realmu odmítne stejně všechny. Po takovém přesunu účty jednou odvažte; každý se při dalším přihlášení naváže na nový issuer:

```sql
UPDATE accounts SET issuer = NULL WHERE provider_id = 'oidc';
```

Dělejte to jen pro tentýž realm na nové adrese. Chcete-li lidi záměrně převést do jiného realmu, smažte místo toho jejich staré propojení (řádky `accounts` s `provider_id = 'oidc'`); při dalším přihlášení se znovu propojí podle ověřeného e-mailu.

<span id="sessions" />

## Relace

- První spuštění s jednotným přihlášením ukončí **všechny** existující relace, takže nikdo nezůstane přihlášen přes heslo. Vypnutí a opětovné zapnutí SSO to způsobí znovu.
- Relace trvá `OIDC_SESSION_MAX_AGE` sekund (výchozí 24 hodin) a její délka se nepřidlužuje použitím. Uživatel deaktivovaný u poskytovatele ztratí přístup do Chatterbox v tomto intervalu.
- **Odhlásit se** ukončí pouze relaci Chatterbox. Relace poskytovatele zůstává, takže další **Přihlášení** může automaticky projít bez výzvy.
- Osobní API tokeny nejsou relace a nadále fungují.

<span id="the-almanac" />

## Almanach

Každé přihlášení přes SSO zaznamená osobu (jméno a e-mail) do Almanachu organizace, případně do jejího vlastního almanachu, pokud [Organizace](./organization) není aktivní. Známá osoba je určena podle e-mailu a přebírá aktuální jméno od poskytovatele; přezdívky, poznámky a fakta přidaná v Chatterbox se zachovávají.

<span id="the-organization-account" />

## Účet Organizace

Při jednotném přihlášení je `ORG_ACCOUNT_PASSWORD` volitelné a nikdo se nemůže přihlásit jako účet Organizace: zůstává vlastníkem stromu Organizace, ale nelze se k němu interaktivně přihlásit. Uživatel poskytovatele identity, jehož e-mail se shoduje s `ORG_ACCOUNT_EMAIL`, je odmítnut.

## Oprávnění od poskytovatele identity

Ve výchozím stavu smí Chatterbox používat každý, koho poskytovatel propustí,
a Organizaci spravuje [účet organizace](./organization). S
`AUTHZ_MODE=idp` místo toho poskytovatel uděluje tři oprávnění jako
klientské role přihlašovacího klienta (`OIDC_CLIENT_ID`, nebo
`KEYCLOAK_ROLES_CLIENT`):

| Oprávnění       | Umožňuje osobě                                                  |
| --------------- | --------------------------------------------------------------- |
| `use`           | přihlásit se, používat API klíče, záznamník schůzek a MCP klienty |
| `org.curate`    | [spravovat Organizaci](./organization#curators)                 |
| `access.manage` | měnit ostatním tato tři oprávnění v **Nastavení → Přístupy**     |

`org.curate` a `access.manage` vyžadují `use` a jedno nezahrnuje druhé.
Podporován je pouze Keycloak (`IDENTITY_PROVIDER=keycloak`).

### Nastavení realmu

Lokální příklad spustíte příkazem `docker compose -f docker-compose.local-authz.yml up -d --build --wait`.
Přímo importuje `e2e/authz/keycloak/chatterbox-local-realm.json` s fiktivními
uživateli a veřejnými testovacími údaji. Účty a reset popisuje
`e2e/authz/README.md`. Testovací přihlašovací údaje nepatří do produkce.

Ve vlastním realmu nastavte důvěrného webového klienta se třemi klientskými
rolemi, skupinu pro každé oprávnění a servisního ověřovatele pouze pro čtení.
Připojte standardní client scopes `basic`, `profile`, `email` a `roles`:
ID token musí obsahovat `auth_time`, access token klientské role pod
`resource_access`. Vypněte Full Scope Allowed a explicitně nastavte scope
mappingy popsané níže. Prvnímu správci přidělte přes skupiny `use` i
`access.manage`. Názvy skupin jsou libovolné, aplikace používá jejich UUID.
MCP klienty nastavte podle [MCP dokumentace](./mcp).
`bun scripts/export-authz.ts` vypíše katalog oprávnění aplikace.

Poté nastavte:

```bash
AUTHZ_MODE=idp
IDENTITY_PROVIDER=keycloak
KEYCLOAK_GROUP_USE_ID=...            # the groups' ids, from Keycloak
KEYCLOAK_GROUP_CURATE_ID=...
KEYCLOAK_GROUP_ACCESS_MANAGE_ID=...
KEYCLOAK_VERIFIER_CLIENT_ID=chatterbox-access-verifier
KEYCLOAK_VERIFIER_CLIENT_SECRET=...
```

V lokálním příkladu je `Users` výchozí skupinou nových účtů. Ve vlastním realmu
tuto volbu nastavte podle své politiky. Aplikace automaticky nepřidává dosavadní
uživatele ani neobnovuje odebrané členství.

### Co musí poskytovatel povolit

Administrátoři mění přístup **vlastním** přihlášením, nikdy sdíleným
administrátorským účtem. Změřeno na Keycloaku 26.7.2:

| Operace                                            | Vyžaduje                      |
| -------------------------------------------------- | ----------------------------- |
| vypsat osoby, číst jejich skupiny a efektivní role | `realm-management/view-users` a `view-clients` |
| přidávat do spravovaných skupin a odebírat z nich  | `realm-management/manage-users` |
| odhlásit osobu u poskytovatele                     | `realm-management/manage-users` |

Správcovské skupině přidělte `manage-users` a `view-clients`
a obě role zahrňte do scope mappingu přihlašovacího klienta. Při vypnutém
Full Scope Allowed samotné členství ve skupině nestačí. Ověřovatel má
`view-users` a `view-clients` jak na service accountu, tak ve scope mappingu.
MCP klienti nedostávají žádné role `realm-management`.

`view-clients` pokrývá nasazení omezující čtení klientských rolí: požadavek
na role skupiny jinak může vrátit prázdný výsledek nebo HTTP 403.
Umožňuje čtení klientů v celém realmu, nikoli jejich úpravy.
Běhové přihlašovací údaje nepotřebují `manage-clients` ani `realm-admin`.

### Relace

- Přihlášení je odmítnuto dřív, než vznikne jakýkoli účet, pokud
  poskytovatel neudělí `use`. ID token i access token se ověřují (podpis,
  issuer, audience, expirace, klient).
- Tokeny poskytovatele se uchovávají pro každou relaci zvlášť, šifrovaně,
  pouze na serveru; nikdy se nedostanou do prohlížeče a zanikají s relací.
- Relace si u poskytovatele znovu ověřuje svá oprávnění každých
  `AUTHZ_VERIFICATION_MAX_AGE` sekund (výchozí 30 minut). Relace, kterou
  poskytovatel ukončil, nebo osoba, která ztratila `use`, je odhlášena;
  dokud poskytovatel není dostupný, požadavky jsou odmítány (503), nikdy
  obslouženy se starými oprávněními.
- Změna přístupu vyžaduje přihlášení u poskytovatele mladší než
  `AUTHZ_ADMIN_MAX_AUTH_AGE` (výchozí 8 hodin). Po vypršení nabídne obrazovka
  nové přihlášení s `prompt=login` a `max_age=0`, které se vrátí do nastavení
  přístupů. Rozpracovaná změna se automaticky neodešle.
- Účet je vázán na issuer, který za něj ručil; viz
  [Stávající účty](#existing-accounts).

### API klíče a záznamník schůzek

Klíč funguje jen tak dlouho, jako přístup jeho držitele. Přístup držitele
se znovu ověřuje přes ověřovatele přístupu nejvýše jednou za
`AUTHZ_VERIFICATION_MAX_AGE` sekund, bez jeho webového přihlášení, takže
záznamník může nahrávat celé týdny. Držitel deaktivovaný nebo smazaný u
poskytovatele je při dalším ověření odmítnut (403); dokud poskytovatel
nebo ověřovatel není dostupný, klíč odpovídá 503 a záznamník si nahrávku
ponechá a zkusí to znovu. Bez ověřovatele funguje klíč, dokud poslední
ověření není starší než `AUTHZ_VERIFICATION_MAX_AGE`, a znovu po dalším
webovém přihlášení držitele.

Odebrání `use` v **Nastavení → Přístupy** okamžitě zablokuje klíče a
záznamník držitele a odhlásí ho všude. Vrácení přístupu odblokuje tytéž
klíče; záznamník nabídne opakování toho, co si ponechal.

### Jak rychle přístup končí

| Změna                                       | Projeví se                                     |
| ------------------------------------------- | ---------------------------------------------- |
| `use` odebráno v Nastavení → Přístupy       | okamžitě: relace, API klíče, záznamník, MCP    |
| oprávnění změněno v Nastavení → Přístupy    | při dalším požadavku osoby                     |
| osoba deaktivována nebo smazána u poskytovatele | při prvním požadavku po vypršení posledního ověření (nejvýše `AUTHZ_VERIFICATION_MAX_AGE`) |
| skupina změněna přímo u poskytovatele       | do `AUTHZ_VERIFICATION_MAX_AGE`                |

Access token, který už AI klient drží, platí až do své expirace (doba
platnosti v realmu, 15 minut u uživatelských MCP klientů v lokálním příkladu);
Chatterbox při každém volání MCP znovu kontroluje `use` dané osoby. Pokud
váš adresář deaktivuje lidi ještě před Keycloakem, celkové zpoždění
zahrnuje i dobu, než se změna do Keycloaku dostane.

Každá změna i odmítnutí se zaznamená do tabulky `access_change_log`: kdo
žádal, pro koho, o co žádal, co má poskytovatel poté uloženo a zda byly
relace osoby ukončeny. Tokeny se nikdy nezaznamenávají. Změna se zaznamená
jako `pending` ještě předtím, než se Chatterbox zeptá poskytovatele, a
doplní se, jakmile skončí; záznam, který zůstal `pending`, tedy označuje
změnu, jejíž výsledek se ztratil (pád, chyba databáze). Ověřte osobu u
poskytovatele.

Odebrání `use` ukončí relace osoby v Chatterbox okamžitě. Když poskytovatel
nedokáže ukončit své relace této osoby, záznam uvádí `pending` nebo
`failed` a obrazovka přístupů osoby nabídne **Ukončit relace** k
opakování. Automaticky se to neopakuje: ukončení vyžaduje vlastní
přihlášení správce, které žádná úloha na pozadí nemá. Do Chatterbox se
osoba v obou případech nedostane.

## Vyzkoušení lokálně

End-to-end stack v repozitáři má Keycloak override s testovacím realm (`riffado-e2e`, uživatelé `alice`, `bob`, `carol`, `dave`, všichni s heslem `<name>-password`):

```bash
RIFFADO_E2E_APP_URL=http://localhost:3310 \
docker compose -f docker-compose.e2e.yml -f docker-compose.e2e.sso.yml up -d --build
```

Chatterbox pak běží na `http://localhost:3310` a Keycloak na `http://localhost:8180`, oba na loopbacku. Realm je pouze pro testování: administrátorem je `admin/admin` a všechna hesla jsou veřejná.
