The `/api/v1/*` surface is Chatterbox's public, stable API.
Personal API keys authenticate it; integrations like Zapier, n8n, and
your own scripts call into it.

For creating keys and configuring webhooks, see
[Automation API and webhooks](../guides/automation-and-webhooks).

## Base URL

`https://<your-chatterbox-host>/api/v1`

That's whatever you set `APP_URL` to in your `.env`.

## Authentication

Send your personal API key as a Bearer token:

```http
Authorization: Bearer op_K7vR8x...
```

Keys are 27 characters: `op_` + 24 URL-safe random characters. Standard keys
carry read scope; paired recorder keys also carry `recordings:write`. Revoked or expired keys are rejected with
`401 UNAUTHORIZED`. Tokens are HMAC-hashed at rest.

## Rate limits

Two buckets enforced on every `/api/v1/*` request:

- **Per IP** — 1,200 requests/minute. Rejects unauth'd flooders.
- **Per authenticated user** — 600 requests/minute.

Limit responses are JSON with a `Retry-After` header and these
RateLimit headers:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 17
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1700000017
```

```json
{
  "error": "Rate limit exceeded",
  "code": "RATE_LIMITED",
  "details": { "retryAfter": 17, "limit": 600, "remaining": 0, "resetAt": 1700000017 }
}
```

## Error envelope

Every error response follows the same shape:

```json
{
  "error": "Human-readable message",
  "code": "MACHINE_READABLE_CODE",
  "details": { "field": "limit" }
}
```

Common codes you should handle:

| Code                     | HTTP | Meaning                                              |
| ------------------------ | ---- | ---------------------------------------------------- |
| `UNAUTHORIZED`           | 401  | Missing, malformed, revoked, or expired key          |
| `FORBIDDEN`              | 403  | Authenticated but not allowed                        |
| `ACCOUNT_SUSPENDED`      | 403  | User account is suspended                            |
| `INVALID_INPUT`          | 400  | A query param or body field failed validation        |
| `RECORDING_NOT_FOUND`    | 404  | Recording id doesn't exist (or isn't yours)          |
| `NOT_FOUND`              | 404  | Generic — e.g. transcript not yet produced           |
| `RATE_LIMITED`           | 429  | Hit one of the buckets above                         |

The `error` field is safe to display. Never parse `error`; branch on
`code`.

## Endpoints

### List recordings

```http
GET /api/v1/recordings
```

Query parameters (all optional):

| Param               | Type           | Notes                                              |
| ------------------- | -------------- | -------------------------------------------------- |
| `limit`             | int (1–100)    | Page size. Default 50.                             |
| `cursor`            | opaque string  | From a previous response's `next_cursor`.          |
| `created_since`     | ISO timestamp  | Filter to recordings created at or after this time.|
| `updated_since`     | ISO timestamp  | Filter to recordings updated at or after this time.|
| `has_transcription` | `true`/`false` | Filter on transcription presence.                  |

```bash
curl -H "Authorization: Bearer op_K7vR8x..." \
  "https://your-host/api/v1/recordings?limit=20&has_transcription=true"
```

```js
const res = await fetch(
  "https://your-host/api/v1/recordings?limit=20",
  { headers: { Authorization: `Bearer ${process.env.CHATTERBOX_KEY}` } },
);
const { data, next_cursor, has_more } = await res.json();
```

Response:

```json
{
  "data": [
    {
      "id": "...",
      "title": "Team standup",
      "created_at": "2026-05-13T12:00:00.000Z",
      "updated_at": "2026-05-13T12:00:00.000Z",
      "recorded_at": "2026-05-13T11:30:00.000Z",
      "duration_ms": 1820000,
      "filesize_bytes": 1234567,
      "device": { "serial_number": "...", "name": "Plaud Note", "model": "..." },
      "has_transcription": true,
      "has_summary": true,
      "audio_reaped": false,
      "processing": { "phase": "summary", "state": "done" },
      "links": {
        "self": "/api/v1/recordings/...",
        "transcript": "/api/v1/recordings/.../transcript",
        "audio": "/api/v1/recordings/.../audio"
      }
    }
  ],
  "next_cursor": "eyJ1cGRhdGVkQXQiOi...",
  "has_more": true
}
```

`audio_reaped` is `true` when the owner's retention policy has deleted
the audio. The recording and its metadata remain; `links.audio` answers
`410 Gone`. Check this flag rather than treating a 410 as an error.

`processing` reports the recording's current workflow phase and that phase's
state. Recordings processed before the workflow report their last settled
phase, or `{ "phase": "categorize", "state": "skipped" }` when they have no
processing row. They do not wait unless new content arrives after the workflow
is enabled.

`phase` is one of `categorize`, `transcribe`, `learn`, `summary`, `taskReview`,
or `share`. `state` is one of `pending`, `waiting`, `running`, `done`, `skipped`,
`failed`, `outdated`, or `not_processed`.

Pagination is **cursor-based, descending by `updated_at`**. When
`has_more` is `true`, pass `next_cursor` back in the next request.
When it's `false`, you've reached the end.

### Get a recording

```http
GET /api/v1/recordings/{id}
```

```bash
curl -H "Authorization: Bearer op_..." \
  https://your-host/api/v1/recordings/01J...
```

Returns the same shape as a list item, plus `transcript` and `summary`
inline when they exist. Returns `404 RECORDING_NOT_FOUND` if the
recording doesn't exist or isn't yours.

### Get a transcript

```http
GET /api/v1/recordings/{id}/transcript
```

```bash
curl -H "Authorization: Bearer op_..." \
  https://your-host/api/v1/recordings/01J.../transcript
```

```json
{
  "language": "en",
  "confirmed_language": null,
  "text": "Full plaintext transcript...",
  "provider": "groq",
  "model": "whisper-large-v3",
  "created_at": "2026-05-13T12:01:23.000Z",
  "turns": [
    {
      "speaker": "speaker_1",
      "start_ms": 18000,
      "end_ms": 40000,
      "text": "Thanks. The project is called Samplee."
    }
  ],
  "corrections": [
    {
      "id": "c-1",
      "turn_index": 3,
      "char_start": 12,
      "char_end": 18,
      "heard": "Samplee",
      "kind": "correct",
      "replacement": "Sample",
      "meaning": "Sample"
    }
  ]
}
```

`language` remains the transcription provider’s detected language. `confirmed_language` is the recording’s user-confirmed ISO 639-1 code, or `null` in Automatic mode. Recording list/detail metadata and webhook recording payloads also include `confirmed_language`; confirmation never replaces provider detection.

`text` is the transcript as it was heard; corrections never rewrite it.
`corrections` lists the confirmed ones as an overlay: an index into
`turns` and UTF-16 offsets into that turn's text. `turns` is null for a
transcript without stored turns (it then has no corrections either); a
turn's `speaker` is the provider's label, never a name. A `correct`
correction replaces the words with `replacement`; a `link` keeps them as
spoken (a nickname, slang) and `meaning` names who or what they refer
to. A `fix` replaces the words with `replacement` too: the automatic
correction pass made it, and `meaning` is the record it names or else the
replacement.

Returns `404 NOT_FOUND` if the recording exists but no transcription
has been produced for it yet. Listen for `transcription.completed`
webhooks to know when to retry.

### Stream audio

```http
GET /api/v1/recordings/{id}/audio
```

```bash
curl -L -H "Authorization: Bearer op_..." \
  -o recording.mp3 \
  https://your-host/api/v1/recordings/01J.../audio
```

Supports HTTP `Range` requests (RFC 7233):

```bash
curl -L -H "Authorization: Bearer op_..." \
  -H "Range: bytes=0-65535" \
  -o head.mp3 \
  https://your-host/api/v1/recordings/01J.../audio
```

- For recordings on **local storage**, the response is the audio bytes
  with `Content-Type` derived from the file extension and
  `Cache-Control: private, max-age=300`. Range requests return `206`
  with `Content-Range`.
- For recordings on **S3 storage**, the response is a `302` redirect
  to a 5-minute pre-signed URL. Follow the redirect (`curl -L`); your
  HTTP client will fetch the audio directly from S3 with no extra
  egress through Chatterbox.

`416` with a `Content-Range: bytes */<size>` header is returned only
for unsatisfiable starts (past EOF or `start > end`). Oversized `end`
values are clamped to `fileSize - 1` per RFC 7233.

## Writes: recording sessions

The read endpoints above accept any key. Writing is gated on the
`recordings:write` scope, which only the streaming recording-session
surface uses. A key with just `read` (the default) cannot call these.

This surface exists for the [Meeting Recorder](../guides/meeting-recorder)
extension, which uploads audio in chunks as it is captured. The flow is:

1. `POST /api/v1/recording-sessions` — open a session. Body includes
   `mimeType` (`audio/webm` or `audio/ogg`), `channelLayout`, `startedAt`,
   and optional `platformHint`, `clientVersion`, `timezoneOffsetMinutes`,
   `noticeAcknowledgedAt`, and `folderId`. The folder must be a non-root
   personal folder or a writable Organization folder. A root folder returns
   `400 INVALID_INPUT`; an unknown or inaccessible folder returns the same code
   with `details.field` set to `folderId`. The `201` response is the full session representation, including
   `folder_id`, `processing`, the one-time `encryption` key, and upload `limits`.
2. `PUT /api/v1/recording-sessions/{id}/chunks/{index}` — upload one chunk as
   the raw request body, with an `X-Chunk-SHA256` header. Indices start at 0
   and must be contiguous. Re-sending an index with the same bytes is a no-op;
   a different body on a taken index is a `409`.
3. `POST /api/v1/recording-sessions/{id}/complete` — declare the session
   finished with `chunkCount`, `endedAt`, and `stopReason`. The server verifies
   every chunk arrived, then assembles and remuxes them into a recording. The
   response carries a `job_id`. Optional `folderId` changes the target before
   finalization: omit it to keep the start folder, send a non-empty string to
   select a folder validated exactly as at creation, or `null` to file later.
   Invalid or inaccessible folders return `400 INVALID_INPUT` with
   `details.field: "folderId"`, leaving the session open for retry. Re-completing
   a session already being finalized does not change its folder. Follow `GET /api/jobs/{job_id}` for progress.
4. `GET /api/v1/recording-sessions/{id}` — status and the list of received
   chunk indices, used to resume after an interruption. Session reads include
   `folder_id` and `processing: { phase, state }`. Before a recording exists,
   processing is `{ "phase": "categorize", "state": "pending" }`; after
   finalization it matches the recording.
5. `DELETE /api/v1/recording-sessions/{id}` — abort and delete buffered chunks.

A paired extension also reads its server defaults from
`GET /api/v1/recorder/config` (same scope): platforms defaulting to **Auto**,
the auto-stop quiet period, the notice text, and whether those **Auto** platforms
are locked. The response also advertises `encrypted_recording_protocol: 1`
and `recording_folder_override: true`. The latter means the complete endpoint
accepts `folderId`; clients of older servers must omit the override and retain
the start folder. The defaults come from the `RECORDER_*` environment variables. Without a
saved choice or a server-selected **Auto** mode, extension 0.3.0 defaults to
**Prompt** for Meet, Teams and Zoom web, and **Off** for other platforms.

The same recorder key can call `GET /api/v1/recorder/folders`. It returns the
key holder's non-root personal folders and writable Organization folders:

```json
{
  "data": [
    { "id": "...", "name": "Client A", "path": "Private / Client A", "scope": "personal" },
    { "id": "...", "name": "Sales", "path": "Organization / Sales", "scope": "org" }
  ]
}
```

Folders are sorted with personal folders first, then by `path`. This endpoint
uses the recorder-key rate limit: a missing or invalid key returns `401`, a key
without `recordings:write` returns `403`, and an exhausted bucket returns `429`.

When `folderId` is present, finalization applies that placement before the
workflow advances. An Organization placement starts as sharing intent; it
continues automatically once a usable folder profile resolves, or waits in the
app for a profile choice or curator action.
When the final target folder is null, the recording waits in the app for its owner to file
it. Consequently, `transcription.completed` and `summary.completed` webhooks for
such a recording are not sent until the owner files it and processing reaches
those phases.

### Sealed recordings

When recorder config includes `features.offlineRecording: 1`, it returns the
paired user's opaque `account.id` and an `offlineKey` with `kid`,
`alg: "ECDH-P256-HKDF-SHA256-A256GCM"`, and `publicKey` (P-256 SPKI as
unpadded base64url). The account ID stays the same across recorder key changes.

`POST /api/v1/recording-sessions/sealed` accepts the normal creation fields
plus `encryption: { protocol: 2, kid, ephemeralPublicKey, salt }`. The
ephemeral key is a 65-byte uncompressed P-256 point and the salt is 16 bytes,
both in unpadded base64url. Derive the chunk key with P-256 ECDH and HKDF-SHA256,
using the UTF-8 string `chatterbox-recorder-offline-v1:<kid>:<clientRecordingId>`
as HKDF info. The response includes `encryption: { protocol: 2, kid }` and
the usual limits. The chunk envelope and its associated data stay at version 1.

Creation returns `201`. An exact retry returns `200` with the current session,
including a replacement or terminal session. Changing the encryption descriptor, start time, notice
acknowledgement, MIME type, or channel layout for the same `clientRecordingId`
returns `409`. Folder, live agenda and room changes do not cause conflicts.
Unavailable folder and live agenda choices at creation are skipped.
An unavailable account key returns `410 OFFLINE_KEY_UNAVAILABLE`.
`POST /api/v1/recording-sessions/{id}/recover` can replace a swept or failed
sealed session and re-derive its chunk key after expiry. A replay or recovery
that returns an open replacement restores its chunk key and active binding.
`DELETE /api/v1/recording-sessions/{id}?capture=1` resolves the current sealed
session from any of its session IDs. A successful response includes
`capture_discarded: true` and a `capture_outcome` of `"discarded"` for a
cancellation or `"completed"` if the recording was already saved. The request
can be retried and returns `409` while the session is finalizing. Sealed replay
and capture cancellation require the original recorder key. A different key
for the same account returns `403 RECORDER_KEY_MISMATCH`. When a selected
folder is unavailable at completion, Chatterbox saves the sealed recording
for filing later. Finalized recordings appear in archives as usual. Resuming
an unfinished upload after a restore requires the original database and
encryption secret.

### Live room recorders

`features.roomRecorders: 1` is available in self-hosted Organization mode.
The owner can send `POST /api/v1/recording-sessions/{id}/lease` with
`{revision, room}` to advertise a live capture for 60 seconds. Use a canonical
room string such as `meet:abc-defg-hij` or `zoom:12345678901`. A higher revision
moves or clears the room (`room: null`). The same revision can refresh the
same room. Send a higher revision to
`POST /api/v1/recording-sessions/{id}/lease/end` to end the lease permanently.
A refused transition returns `409 RECORDING_LEASE_REFUSED`.

`POST /api/v1/recorder/rooms/recorders` accepts one room in `{room}` and returns
`{data: [{name}], live_until, freshForMs}`. It lists other eligible Organization members
currently recording in that room, once per member. `live_until` is the earliest
lease expiry across the listed captures as an ISO 8601 timestamp. `freshForMs`
is the remaining time until that expiry in milliseconds, measured by the server.
The extension counts elapsed lookup time against that lifetime and caps it at
30 seconds. A member who knows the exact room identifier can make this lookup.
An empty result returns `{data: [], live_until: null, freshForMs: 0}`.
The lookup allows 48 requests per minute per account and 480 per minute per IP,
subject to the general API limits.

There are no other public write endpoints. To push finished audio in through
the UI instead, use the upload button in the dashboard.

## Stability

The `/api/v1/*` surface is a versioned public contract. Once shipped:

- Existing endpoints don't get breaking changes — fields are added,
  not repurposed.
- Error `code` values are stable. New codes get added; old ones don't
  get renamed.
- Removals or breaking changes go through a deprecation cycle with a
  CHANGELOG note.

If you need a new field, capability, or endpoint, file an issue. The
shape gets discussed there before it ships.
